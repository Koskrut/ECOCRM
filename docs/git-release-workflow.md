# Git: как правильно выпускать релиз (под текущий CI)

Опирается на `.github/workflows/publish-release.yml`.

## Что запускает сборку

| Способ | Что сделать в Git |
|--------|-------------------|
| **Тег** | Запушить аннотированный тег вида **`v0.2.140`** (префикс `v`, дальше semver). Workflow срабатывает на `push` тегов `v*`. Версия образов = имя тега **без** `v`. Чеклист: [`docs/RELEASING.md`](RELEASING.md). |
| **Вручную** | В GitHub: **Actions → Publish Registry Release → Run workflow** — версия из поля `version` (без `v`), ветка/run из UI определяет **какой коммит** соберётся. |

## Рекомендуемая последовательность (тег)

1. Слить нужные изменения в **`main`** (или в релизную ветку, если у вас так принято).
2. **`git pull`** на актуальном `main`, прогнать тесты/сборку локально при необходимости.
3. Создать тег **на том коммите**, который должен уйти в registry:
   ```bash
   git checkout main && git pull
   git tag -a v0.2.140 -m "Release 0.2.140"
   git push origin v0.2.140
   ```
4. Дождаться успешного **Publish Registry Release** (образы + manifest + при наличии секретов — Control Plane).

Важно: **сначала пуш коммитов**, потом тег на уже существующий на `origin` коммит — иначе CI может не найти нужное состояние.

## Имя тега и совместимость

- В README зафиксирована текущая линия **`0.2.x`** для новых релизов; линия **`0.1.x`** — для уже развёрнутых клиентов до перехода.
- Для тегов **`v0.2.*`** при пустом CSV **modules** в CI собираются все опциональные module-образы (см. `publish-release.yml`).
- **`v1.0.0`** в README помечен как зарезервированный под первый платный production-клиент — не использовать «случайно» для обычных патчей, если следуете этому правилу.

## Без тега (только ручной запуск)

- Удобно для **тестового** или срочного билда с полем `version` (например `0.2.7-rc1`), не создавая тег в Git.
- Ясно выбрать **branch** (обычно `main`), чтобы SHA в manifest совпадал с ожидаемым кодом.

## Связь с клиентом

- Клиент подтягивает образы по **тегу версии** из registry (как в README: `BACKEND_VERSION`, `WEB_VERSION` и т.д. в `.env`).
- Отдельно на сервере: **migrate** при смене версии с миграциями.

## Опционально до тега

- Workflow **Preflight Release Build** (`workflow_dispatch`) — сборка без push в registry, проверка manifest; не заменяет publish-release.
