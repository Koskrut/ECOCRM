# Workflow онбординга нового клиента (пример: bio3ua, core-only)

Чёткая последовательность для команды: от договора до рабочей CRM на сервере клиента. Под «новым клиентом» имеется в виду **первичная поставка** (ещё нет боевых данных или миграция с пустой схемы).

---

## Фаза A — до сервера клиента

### A1. Договор и SKU

- Зафиксировать **имя клиента**, окружение (`prod` / `staging`), **список модулей в подписке** на старте (для bio3ua может быть **только core**).
- Выбрать **версию релиза** (тег образов), с которой стартуем, и канал (`stable` / `beta`).

### A2. Секреты и артефакты

- Подготовить для клиента (без отправки в открытом виде): `DATABASE_URL`, `JWT_SECRET`, пароль первого ADMIN, при необходимости ключи интеграций **позже**.
- **Лицензия** (`license.json`) или активация через **Control Plane**: в payload перечислены **только** модули из SKU (для чистого core — по сути только базовое ядро; расширения не включать).

### A3. Compose / образы

- Для **core-only**: образы `crm-core-api`, `crm-web`, Postgres; **без** `crm-module-*`, если модулей в SKU нет.
- Файлы: `compose.base.yml` + `compose.client.yml` + при необходимости только те overlays, которые реально нужны (без модульных sidecar).

---

## Фаза B — на сервере клиента (первый выкат)

### B1. Инфраструктура

- Поднять **Postgres** (персистентный volume, бэкап-политика согласована).
- Сеть, TLS (reverse proxy), диск под uploads если нужно.

### B2. Переменные окружения (минимум)

- `DATABASE_URL`, секреты приложения, `LICENSE_FILE_PATH` (или режим CP + токены установки).
- `BACKEND_VARIANT=core` для сервиса API, если используется **crm-core-api**.
- `API_URL` у **web** — URL backend, доступный из браузера пользователя.

### B3. Миграции БД

- **Один раз до** первого старта приложения с новой версией: `prisma migrate deploy` (или ваш контейнер `backend-migrate` из compose).
- Убедиться, что миграции прошли без ошибки.

### B4. Запуск стека

- `docker compose up -d` (ваш набор `-f`).
- Проверить логи `crm-core-api` / `web`: нет падения на старте, коннект к БД.

### B5. Первый вход и учётка

- Создать **первого пользователя ADMIN** (seed / ручная регистрация / ваш скрипт — как принято у вас).
- Войти под ADMIN.

### B6. Проверка «здоровья»

- Открыть **`/settings/health`**: версия, лицензия, модули, при CP — блок control plane.
- Вызвать при необходимости `POST /rbac/sync-defaults` (ADMIN) для каталога прав.

### B7. Включённые модули (pilot) — текущая реальность кода

- Сейчас флаг **`enabled`** для расширений берётся из **SystemSetting (pilot)** или fallback, если запись ещё не создавалась.
- Для клиента **только с core в SKU**: либо **не трогать** pilot до первого сохранения (часто всё лицензированное становится доступным при отсутствии записи — уточните по своему шаблону БД), либо явно выставить список через **`PUT /system/modules/enabled`** / UI **Pilot modules** под согласованный SKU.
- **Цель на будущее (авто от подписки):** вынести в отдельную задачу режим «`enabled` = лицензия», чтобы не зависеть от ручного pilot.

### B8. Продуктовый минимум в CRM

- Компания / воронки / справочники по шаблону клиента.
- При необходимости: metadata (поля, словники), импорт контактов (`/settings/data-import`).

### B9. Handover клиенту

- Передать: URL, учётку ADMIN (или процедуру смены пароля), куда писать в поддержку, **что в подписке** и **что включено** на сервере.

---

## Фаза C — позже: клиент докупил модули

### C1. Коммерция

- Обновить подписку / выдать новый **`license.json`** (или entitlement в CP) с **новыми module id**.

### C2. Поставка на сервер

- Подтянуть образы **`crm-module-*`**, добавить нужные **`compose.modules.*.yml`**, задать env (upstream URL, ключи провайдера).
- При смене только лицензии без новых образов — перезапуск backend после подмены файла лицензии / обновления секретов.

### C3. Миграции

- Если в релизе с модулем есть **новые миграции** — снова `migrate deploy` перед включением трафика.

### C4. Включение в CRM

- Обновить **pilot / `PUT /system/modules/enabled`**, чтобы новый модуль был в списке **enabled** (пока нет авто-режима от лицензии).
- Проверить **`GET /system/modules`**: `licensed`, `enabled`, `effective` для нового модуля.

### C5. Smoke модуля

- Пройти 1–2 ключевых сценария (например, тестовый звонок / тестовая відправка — по типу модуля).

## Ответственность границ

| Зона | Кто |
|------|-----|
| Версия образов, манифест релиза | Ваша CI / registry |
| Лицензия (что можно) | Вы / Control Plane |
| Что физически крутится на сервере | Клиент или ваш managed deploy |
| Что включено в приложении (`enabled`) | Сейчас — pilot + лицензия на `effective`; позже — можно автоматизировать |

*Документ можно копировать в Confluence/Notion и подставлять имя клиента и даты.*
